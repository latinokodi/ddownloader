## The five decisions that block the build (recommend resolving first)

1. **Engine strategy (P06/P07/P28):** Kotlin re-implementation of a subset of engines vs Chaquopy hosting the unmodified qBittorrent plugins vs dropping metasearch behind a remote proxy. This decides app size, Python runtime, and CF-solver existence.
2. **Storage strategy (P19/P25):** SAF tree root + `DocumentFile` (slow but Play-safe) vs `MANAGE_EXTERNAL_STORAGE` (fast but policy-risky) vs app-private dir only (no Jellyfin integration). The Jellyfin layout is worthless if the media cannot be seen by other apps.
3. **Background model (P14/P17):** foreground service with 10 s poll (battery cost, notification required) vs WorkManager periodic (15 min minimum, download restarts) vs “download only while app is open”. The desktop app assumes an always-running process.
4. **Update channel (P27/P31):** Play-only vs direct APK (Obtainium) — decides whether an in-app updater is needed at all and what signing/verification is required.
5. **Tor scope (P36):** global SOCKS (all debrid API + CDN traffic) vs scrape-only routing vs opt-in per-feature. Debrid providers and CDNs commonly block Tor exits; global routing may break the core download path and must be a product decision, not a transport detail.

## Test harness notes

- Port the existing 12 `media-layout` vectors unchanged (`src/__tests__/media-layout.test.ts`) — they are the cheapest objective parity gate for layout/rename naming.
- Build a local fake CDN in tests (OkHttp `MockWebServer`) that can answer `206`/`200`/`416`, truncate, and redirect off-allowlist; this covers the most dangerous engine semantics without network.
- Golden files for `parseReleaseName`, status formatting, and provider normalizers; fixture HTML saved per engine/provider (the desktop app has no such fixtures — creating them is part of the port).
- Manual device checks that cannot be unit-tested: SAF permission persistence, foreground-service notification, Tor bootstrap, WebView CF solve rate, Play update flow.
